## 1. Реализация osago-aggregator и его хранилище

**Назначение osago-aggregator:**

- Инкапсулирует интеграции с внешними страховыми компаниями по ОСАГО (REST к страховым).
- Реализует паттерн scatter‑gather: параллельно рассылает заявки во все страховые, опрашивает их API «получить предложение», агрегирует ответы.
- Возвращает в core-app поток/набор предложений по одной заявке по мере их поступления.

**Нужно ли своё хранилище?**
Да, небольшой **per‑service** PostgreSQL (отдельная схема/БД) ему нужен.

Что хранить:

- Таблица заявок ОСАГО: `osago_request`
  - `id` (внутренний id),
  - `core_request_id` (идентификатор заявки в core-app),
  - данные автомобиля (или ссылку на агрегированное DTO),
  - состояние заявки (NEW, SENT, COMPLETED, EXPIRED),
  - общие тайм‑ауты (deadline = now + 60 сек).
- Таблица заявок в страховые: `company_request`
  - `id`,
  - `osago_request_id`,
  - `insurance_company_id`,
  - внешний идентификатор заявки в страховой,
  - статус (NEW, SENT, FAILED, COMPLETED, TIMEOUT),
  - метаданные по ретраям, последнему запросу.
- Таблица предложений: `company_offer`
  - `id`,
  - `company_request_id`,
  - премия, франшиза, покрытие, валюта и т. п.

Назначение хранилища:

- Позволяет горизонтально масштабировать osago-aggregator (несколько реплик в Kubernetes шарят одну БД/кластер).
- Даёт возможность ретраев, анализа тайм‑аутов, идемпотентности.
- Позволяет дослать предложения в core-app (через события/REST) даже при временных сбоях.

***

## 2. API osago-aggregator для core-app

- osago-aggregator может публиковать события `OsagoOfferReceived` в Event Streaming Platform (Kafka) в топик, например, `osago.offers`. core-app будет подписчиком.
- Структура события: `requestId`, `coreRequestId`, `insuranceCompanyId`, данные предложения.

***

## 3. Интеграция core-app и osago-aggregator

Рекомендуемый основной вариант: **REST + event streaming**.

### Поток запросов

1. Пользователь отправляет форму ОСАГО во фронтенд.
2. Фронтенд вызывает REST‑API core-app.
3. core-app:
   - валидирует данные, сохраняет сущность «заявка ОСАГО» в своей БД (`core-db`),
   - синхронно вызывает `POST /api/osago/requests` у osago-aggregator, передавая `coreRequestId`.
4. osago-aggregator создаёт запись у себя, запуск scatter‑gather на страховые.
5. osago-aggregator публикует `OsagoOfferReceived` в Kafka; core-app слушает и пушит фронту обновления.

***

## 4. API для веб‑приложения (frontend ↔ core-app)

Фронтенд уже общается с core-app по REST.

Новые/изменённые эндпоинты в core-app:

1. `POST /api/osago/quotes`

- Вход: данные автомобиля, водителей и т. п.
- Поведение:
  - core-app создаёт заявку ОСАГО у себя,
  - создаёт агрегационную заявку в osago-aggregator (см. выше),
  - возвращает клиенту `osagoRequestId` (идентификатор агрегации) и, возможно, уже полученные первые предложения, если есть.

2. `GET /api/osago/quotes/{osagoRequestId}` и/или WebSocket/SSE‑endpoint `GET /api/osago/quotes/{osagoRequestId}/stream`

SSE, по мере получения новых предложений core-app пушит их в браузер.

- Возвращает:
  - полный список предложений на текущий момент,
  - признак завершённости сбора,
  - оставшееся время/тайм‑аут.

## 5. Паттерны отказоустойчивости и где их применить

### 5.1. osago-aggregator ↔ страховые компании (внешние REST API)

Здесь критично:

- **Timeout**:
  - Жёсткий тайм‑аут на вызов каждой страховой, например 3–5 секунд на создание заявки и 3–5 секунд на опрос предложения, с учётом 60 секунд SLA на весь процесс.

- **Retry**:
  - Ограниченный, с backoff (например, 2–3 попытки) на временные ошибки (5xx, network).
  - Идемпотентность обеспечивается за счёт того, что страховые API обычно либо поддерживают идемпотентные ключи, либо допускают повторение при неизменном requestId.

- **Circuit Breaker**:
  - Для каждой страховой — отдельный breaker.
  - При постоянных ошибках/тайм‑аутах по конкретной компании breaker открывается, osago-aggregator помечает эту компанию как временно недоступную и не портит SLA всей операции.

- **Rate Limiting**:
  - Можно реализовать per‑company лимиты (не слать больше N RPS в одну страховую, чтобы не попасть под их ограничения).

На схеме:
На стрелках osago-aggregator → страховые подписать `REST + Timeout + Retry + Circuit Breaker + Rate Limiting`.

### 5.2. core-app ↔ frontend

- **Timeout**:
  - Настраивается на уровне API‑gateway / ingress (например, 30–60 секунд для long‑polling, но лучше делать короткие запросы и/или SSE).

- **Rate Limiting**:
  - На уровне внешнего ingress / API Gateway — для защиты от всплесков со стороны веб‑клиентов и партнёров (это уже соответствует проблеме с B2B партнёром из описания).

На схеме можно отметить rate limiting на внешней границе (LoadBalancer / API Gateway).

### 5.3. Event Streaming Platform

- Kafka сама по себе обеспечивает устойчивость и горизонтальное масштабирование.
- Паттерны timeout/retry реализуются через consumer‑конфигурацию (retry, DLQ).

## 6. Учитываем несколько экземпляров сервисов

Сервисы уже задеплоены в нескольких экземплярах в Kubernetes.

Следствия:

- osago-aggregator:
  - Должен использовать общую БД и, при необходимости, механизмы блокировок/маркировки задач, чтобы один запрос ОСАГО не обрабатывался параллельно разными инстансами.
  - HTTP‑клиенты к страховым и Kafka‑консьюмеры следует настраивать с учётом горизонтального масштабирования (consumer group, partitioning).

- core-app:
  - При использовании событий `osago.offers` — один consumer group на core-app; разные инстансы делят партиции.
