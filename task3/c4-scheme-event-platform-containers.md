## Участники

- Клиент (Person): пользователь web‑сайта InsureTech, оформляет и просматривает страховки, выполняет оплату через внешнюю платёжную систему.
- Платёжный сервис (Software System): внешняя платёжная система, через которую проводится оплата страховок; деньги уходят на счета страховых компаний.
- Системы партнёров (Software System): внешние системы партнёров, интегрирующие страховые услуги InsureTech в свои продукты через B2B API.
- Системы страховых компаний (Software System): ИТ‑системы страховых компаний, предоставляющие API для получения актуальных тарифов, андеррайтинга и оформления страховых продуктов.

***

## Граница системы

- Виртуальная машина «InsureTech Prod» — внутри неё развернуты контейнеры с приложениями и БД (кластер Kubernetes в одной зоне доступности), а также платформа потоковой обработки событий (Kafka/совместимый брокер).

***

## Внутренние контейнеры и базы данных

1. InsureTech Web
   - Тип: веб‑приложение.
   - Технологии: JavaScript, React.
   - Ответственность:
     - интерфейс для клиентов;
     - подбор и оформление страховок через REST API backend;
     - редирект клиента в платёжный сервис для проведения оплаты.

2. core-app
   - Тип: монолитное backend‑приложение.
   - Технологии: Kotlin, SpringBoot.
   - Ответственность:
     - отображение доступных страховых продуктов и тарифов на основе локальной реплики данных (получаемой по событиям из брокера);
     - оформление заявок и выпуск полисов;
     - отображение уже оформленных страховок;
     - инициирование платежей во внешний платёжный сервис;
     - публикация доменных событий о полисах (PolicyIssued/PolicyUpdated/PolicyCancelled) в Event Streaming Platform через паттерн Transactional Outbox.

3. client-info
   - Тип: сервис управления клиентскими данными.
   - Технологии: Kotlin, SpringBoot.
   - Ответственность:
     - хранение и предоставление клиентских данных core-app для оформления страховок;
     - создание/обновление клиентских данных при их отсутствии или изменении;
     - отображение и редактирование данных клиента в личном кабинете.

4. ins-product-aggregator
   - Тип: сервис интеграции со страховыми компаниями.
   - Технологии: Kotlin, SpringBoot.
   - Ответственность:
     - получение информации о страховых продуктах и тарифах от внешних систем страховых компаний по их API;
     - запрос предложений по ОСАГО для конкретного автомобиля у разных партнёров;
     - агрегирование данных страховых компаний и публикация событий изменений продуктов и тарифов (ProductUpdated/TariffUpdated/ProductRemoved) в Event Streaming Platform (topic `products.tariffs`), вместо синхронной выдачи полного списка по запросу других сервисов.

5. ins-comp-settlement
   - Тип: сервис взаиморасчётов со страховыми компаниями.
   - Технологии: Kotlin, SpringBoot.
   - Ответственность:
     - приём событий оформленных страховок (policies.events) и поддержание собственного хранилища данных для взаиморасчётов;
     - приём событий продуктов и тарифов (products.tariffs) и поддержание локальной реплики тарифов;
     - учёт оформленных страховок для расчёта агентских вознаграждений;
     - формирование и периодическая отправка перечня оформленных страховок в страховые компании для расчёта выплат;
     - опционально — использование REST API core-app для получения списка полисов как fallback‑механизма (legacy), основным источником данных являются события.

6. Event Streaming Platform
   - Тип: инфраструктурный сервис (Kafka / совместимый брокер сообщений и событий).
   - Ответственность:
     - транспорт и хранение событий продуктов и тарифов (topic `products.tariffs`), публикуемых ins-product-aggregator и потребляемых core-app и ins-comp-settlement;
     - транспорт и хранение событий полисов (topic `policies.events`), публикуемых core-app через Transactional Outbox и потребляемых ins-comp-settlement (и потенциально другими сервисами/аналитикой);
     - обеспечение горизонтального масштабирования и декуплинга между сервисами при росте числа страховых компаний и объёма оформляемых полисов.

7. core-db
   - Тип: база данных PostgreSQL.
   - Ответственность:
     - хранение тарифов страховых компаний и заявок клиентов на страховые продукты (схема данных core-app);
     - хранение полисов;
     - хранение таблицы outbox_events, используемой паттерном Transactional Outbox для надёжной публикации событий в Event Streaming Platform в одной транзакции с бизнес‑данными.

8. ins-comp-settlement-db
   - Тип: база данных PostgreSQL (логически используется как хранилище для двух доменных областей).
   - Ответственность:
     - хранение данных клиентов (ФИО, паспорт, телефон и прочая информация, необходимая для оформления страховок и взаимодействия со страховщиками) в контексте взаиморасчётов;
     - хранение данных об оформленных страховках, условиях взаиморасчётов со страховыми компаниями и локальных реплик тарифов, формируемых на основе событий из брокера.

## Основные взаимодействия (на уровне контейнеров)

- Клиент и системы партнёров взаимодействуют с InsureTech Web и core-app по REST для подбора и оформления страховок, а также просмотра оформленных полисов.
- core-app синхронно взаимодействует с client-info и его БД для работы с клиентскими данными, а также с платёжным сервисом по HTTP для проведения оплат.
- ins-product-aggregator синхронно опрашивает внешние системы страховых компаний по их API, но внутрь InsureTech публикует изменения продуктов и тарифов в виде событий в Event Streaming Platform (event streaming).
- core-app и ins-comp-settlement подписываются на события `products.tariffs` и поддерживают свои локальные реплики продуктово‑тарифных данных в собственных БД, что убирает прямую синхронную зависимость от ins-product-aggregator.
- core-app при оформлении/изменении полиса записывает изменения в core-db и событие в outbox_events в одной транзакции (Transactional Outbox), после чего отдельный процесс/CDC надёжно публикует события в topic `policies.events` в Event Streaming Platform.
- ins-comp-settlement подписывается на `policies.events`, формирует своё состояние по полисам в ins-comp-settlement-db и использует его для расчёта взаиморасчётов и формирования реестров, вместо тяжёлого ночного REST‑запроса к core-app (который остаётся как резервный канал).
